**Stop hardcoding a single model ID across routine extractions and deep refactors.** `enso-auto` starts at `enso-flash` and escalates only when the router or Kai judges a prompt needs `enso-pro`, `enso-max`, or `enso-ultra`.

## Architecture & contract

Enso classifies each prompt on CPU (`12 µs` for the learned policy), filters to models your org can serve, and bills strictly at the tier that answered. `X-Routed-Model` and the response body's `routing` object report the chosen tier and reason.

**Primary endpoint:** `POST /v1/chat/completions` · **Status:** `shipped` · **Level:** `foundations`

## Run it across all four surfaces

<Tabs items={['CLI', 'SDK', 'HTTP', 'MCP']}>
<Tab value="CLI">
```bash
hanzo chat completions --data '{
  "model": "enso-auto",
  "reasoning_effort": "auto",
  "messages": [{"role": "user", "content": "Explain why a B-tree beats a hash index for range queries."}]
}'
```

import { Configuration, AiApi } from 'hanzoai';

const ai = new AiApi(new Configuration({ accessToken: process.env.HANZO_API_KEY }));
const { data } = await ai.postChatCompletions({

## Verify the outcome

- Inspect `X-Routed-Model` in the HTTP response headers.
- Compare a trivial one-line extraction (routes to `enso-flash`) vs. a multi-file architecture critique (escalates to `enso-pro`/`enso-max`).

## Production guardrails

- Pass `reasoning_effort: "instant"` for latency-sensitive formatting calls where extended thinking adds zero value.
