# Traces

> **API reference** · [Traces →](/docs/openapi/traces) — every endpoint, generated from the OpenAPI spec.

A trace is one end-to-end request or agent run, made of nested **spans**. A span
is a unit of work with a start, an end, a name, and attributes; the parent links
between them are what turn a pile of spans into a waterfall.

There are two ways to read a trace, and which you want depends on the question.
For "what happened, in what order, and how long did each part take", read spans.
For "which model answered and what did it cost", read
[observations](/docs/observations).

## Append spans

```bash
curl -X POST https://api.hanzo.ai/v1/traces/write \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "spans": [
      {
        "traceId": "7c33a1f0",
        "spanId": "0a91",
        "parentId": "",
        "name": "checkout",
        "startNs": 1760000000000000000,
        "endNs": 1760000001840000000,
        "attrs": { "service.name": "checkout-api", "user.id": "u_42" }
      }
    ]
  }'
```

Answers `{ "written": 1 }`. Times are **nanoseconds** since the Unix epoch. Every
span is indexed by its trace id as it lands, which is what makes the waterfall
read possible without a second store.

Retention is a bounded ring of 1,048,576 spans per org — past that the oldest are
evicted. A long-lived trace can therefore lose its early spans while its later
ones survive, so treat a waterfall read as best-effort against retention.

## Read one trace

```bash
curl "https://api.hanzo.ai/v1/traces/trace?id=7c33a1f0" \
  -H "Authorization: Bearer $HANZO_API_KEY"
```

Answers `{ spans }` — every span your org holds for that id, in the order they
were appended, which is exactly what a waterfall renders. There is no time range
and no limit: a trace is addressed by id or not at all.

An id with no spans answers an **empty list, never a `404`** — the store cannot
tell a trace that never existed from one whose spans retention has already
dropped, so it does not pretend to.

## Scan recent spans

```bash
curl "https://api.hanzo.ai/v1/traces/query?limit=100" \
  -H "Authorization: Bearer $HANZO_API_KEY"
```

Answers `{ count, spans }`, newest first, filtered on each span's start time.
`start` and `end` are nanosecond bounds, where `0` — which is also what an
absent or unparseable value becomes — means unbounded. `limit` defaults to 100.

This lists **spans, not traces**: several spans of one trace each take a slot
against `limit`. Assembling one trace is the call above.

`GET /v1/traces/health` reports how many spans this deployment currently holds
for your org.

## The model's-eye view

For traces that contain model calls, the observability plane rolls the same
activity up per request, per conversation, and per end user:

```bash
curl "https://api.hanzo.ai/v1/o11y/llm/traces?limit=50" \
  -H "Authorization: Bearer $HANZO_API_KEY"
```

Filter with `start` and `end` (unix **milliseconds**), `traceId`, `sessionId`,
`userId`, `name`, `model`, `offset`, and `limit`. The same nine filters work on
`/v1/o11y/llm/observations`, `/llm/sessions`, and `/llm/users`.

Set `session.id` and `user.id` as span attributes and those rollups group
themselves — see [Observations](/docs/observations) for the full attribute
contract.
