# Architecture

This section explains how Hanzo Cloud is put together — what runs today, and where the platform is headed. We keep the two clearly separated: the product pages elsewhere in these docs describe shipped behavior, while the platform direction here is design work being ratified through the [Hanzo Improvement Proposals (HIPs)](https://hips.hanzo.ai). For the principles behind it all, see [Engineering Philosophy](/docs/architecture/philosophy).

## Today

Hanzo Cloud is **one Go binary**. A single API key at `api.hanzo.ai` reaches every capability — AI inference, identity, secrets, storage, commerce, and more — because those capabilities are **native subsystems compiled into that one binary** (`cloud`, `CGO_ENABLED=0`, static), each served under `/v1/<capability>` and described by the one document the binary emits, [hanzoai/cloud](https://github.com/hanzoai/cloud)'s `openapi.yaml`. Ingress and routing are native subsystems too, so the binary is its own entry point rather than sitting behind a separate gateway or ingress tier. This single-binary consolidation is the unified cloud binary (HIP-0106), already substantially shipped — and it is the same binary that powers [the network you can run yourself](/docs/network).

Every capability is grouped into exactly one of **nine domains**. [The reference](/docs/openapi) counts them and lists them all:

Sovereign corporate legal, capital rails, and financial ledgers operate natively across the platform — including [**Sign**](https://github.com/hanzoai/esign) (`esign.hanzo.ai`, [HIP-1125](https://hips.hanzo.ai/hip-1125-esign-signatures)), [**Dataroom**](https://github.com/hanzoai/dataroom) (`dataroom.hanzo.ai`, [HIP-1121](https://hips.hanzo.ai/hip-1121-dataroom-shared-documents)), [**Cap Table**](https://github.com/hanzoai/captable) (`captable.hanzo.ai`, [HIP-1111](https://hips.hanzo.ai/hip-1111-captable)), and the core financial ledger suite: **Treasury** ([HIP-1221](https://hips.hanzo.ai/hip-1221-treasury-the-reserve-fund)), **Ledger** programmable double-entry engine ([HIP-1001](https://hips.hanzo.ai/hip-1001-ledger-double-entry-ledger)), [**Billing**](https://github.com/hanzoai/billing) (`billing.hanzo.ai`, [HIP-1220](https://hips.hanzo.ai/hip-1220-commerce-the-merchant-half)), and **Wallet** ([HIP-1161](https://hips.hanzo.ai/hip-1161-wallet-key-custody)). State across all subsystems is managed by the database-agnostic [**Hanzo ORM**](/docs/projects/hanzoai/orm) ([HIP-0144](https://hips.hanzo.ai/hip-0144-where-state-lives)), defaulting to embedded SQLite for instant local development while seamlessly targeting clustered PostgreSQL, Datastore, and KV engines in production.

## Direction

Hanzo's [self-improvement loop](/docs/self-improvement) connects another part of
the design: everyday task outcomes can improve scoped memory and lead to
validated changes in skills, tools, apps, the agent harness and cloud
infrastructure. It is event-driven, with review before shared product changes
are released. The page distinguishes existing memory machinery from the
end-to-end integration still to be built.

The platform is converging on one model for running these services: a **consensus-backed plugin platform**, where each service is a *plugin* registered into a single cloud runtime, and a small consensus control plane decides where each plugin's writers live. This is a design direction — specified as a draft proposal, not yet a shipped runtime.

<Callout type="info">
The plugin platform is described in **HIP-0125 (Draft)**. It builds on a set of related proposals — the in-process extension runtime (HIP-0105), the unified cloud binary (HIP-0106), streaming replication (HIP-0107), and the ZAP transport (HIP-0114). Draft proposals may change; nothing on the [plugin-platform page](/docs/architecture/plugin-platform) is a shipped user feature.
