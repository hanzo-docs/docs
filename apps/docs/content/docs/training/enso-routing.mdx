**Enso optimizes which generative model answers each request — without sending prompt text into shared training sets.** Every routing call runs in microseconds on CPU, honors your hard cost and latency headers, and learns from your org's own outcome signals.

## 1. Bound every call with cost and latency ceilings

Send `model: "enso-auto"` (or `model: "auto"`) with `X-Max-Cost` (USD per 1,000 tokens) and `X-Max-Latency-Ms` (milliseconds). Read `X-Routed-Model` and `X-Hanzo-Served` from the response headers alongside `id` (`chatcmpl-...`).

## 2. Teach the learned router with outcome rewards

Attach an objective outcome to every routed `request_id` via `POST /v1/ai/feedback`. Enso stores only anonymized request features and the scalar reward — **never prompt or completion text** — scoped strictly to your org.

| `signal` | Reward weight | When to emit |
|---|---|---|
| `accept`, `up` | `1.0` | User accepted output, PR merged, or tests passed on first try |
| `regenerate` | `0.25` | Output needed a retry |
| `down`, `switch`, `abandon`, `revert` | `0.0` | User switched models, reverted patch, or tests failed |
| `rating` (`1`, `2`, `3`) | `0.0`, `0.5`, `1.0` | Explicit graded rubric outcome |
| `dismiss` | ignored | No signal recorded |

```bash
curl -X POST https://api.hanzo.ai/v1/ai/feedback \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"request_id": "chatcmpl-01J...", "signal": "accept"}'
```

Each retraining cycle fits a candidate bilinear policy over your org's reward ledger and promotes it **only if it beats the incumbent on held-out reward**.

## 3. Compose custom org router blends (`enso-<name>`)

When you need explicit arm ordering and bounded fan-out width, inspect existing blends and store an org preset via `POST /v1/benchmark/presets`:

```bash
# Inspect reference blends
curl https://api.hanzo.ai/v1/benchmark/presets \
  -H "Authorization: Bearer $HANZO_API_KEY" | jq '.'

# Store an org-private blend resolved as enso-code-fast
curl -X POST https://api.hanzo.ai/v1/benchmark/presets \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "code-fast",
    "arms": ["zen6-flash", "zen6-coder", "enso-pro"],
    "panel_width": 2
  }'
```

## 4. Validate routing changes with paired benchmarks

Before changing default routing strategy (`GET /v1/ai/org/settings`), run a controlled A/B experiment (`POST /v1/experiment`) or compare two arms on paired items (`GET /v1/benchmark/compare?benchmark=...&a=enso-pro&b=zen6-coder`) so cost savings never hide accuracy drops.
