# Hanzo Memory

Memory gives an assistant something to carry between conversations. You store
short pieces of content as they come up, and later retrieve them by meaning
rather than by key. Every memory is scoped to one user inside one org, so recall
never crosses between people.

Identity comes from your credential — the org and the user are resolved from the
token, never read from the request body — so there is no user id to pass and no
way to write into someone else's memory.

## Remember something

```bash
curl -X POST https://api.hanzo.ai/v1/memory/remember \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "content": "Prefers metric units and a terse writing style.",
    "kind": "user",
    "metadata": { "source": "onboarding" }
  }'
```

`content` is required. `metadata` is free-form string pairs, useful for
provenance and filtering later.

## Kinds

`kind` is one of five values. Anything unrecognized is stored as `user`.

| Kind | For |
|------|-----|
| `user` | Facts about the person — preferences, context, constraints |
| `project` | Context about a piece of work |
| `reference` | Material to look things up in |
| `feedback` | What the person said about a previous answer |
| `fact` | A standalone assertion worth keeping |

A "fact" is a kind, not a separate structure — there is no triple, no confidence
score, and no importance weight. `GET /v1/memory/facts` is exactly a recall
filtered to `kind=fact`, newest first.

## Recall it

Two reads, differing in one way:

```bash
# Semantic search — q is required
curl "https://api.hanzo.ai/v1/memory/search?q=how%20should%20I%20write%20to%20them&limit=5" \
  -H "Authorization: Bearer $HANZO_API_KEY"

# Recall — q is optional. Without it you get the most recent
curl "https://api.hanzo.ai/v1/memory/recall?kind=user" \
  -H "Authorization: Bearer $HANZO_API_KEY"
```

`search` ranks semantically and falls back to text matching. `recall` ranks
semantically when you give it `q`, and otherwise returns the newest first — which
is what you want when priming a conversation with no query yet.

Both take `kind` and `limit` (default 20). `GET /v1/memory/list` is a plain
listing with `kind` and `limit` (default 100).

## Change and remove

```bash
curl -X POST https://api.hanzo.ai/v1/memory/update \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "mem_71ab", "content": "Prefers metric units. Now writes long-form." }'

curl -X POST https://api.hanzo.ai/v1/memory/delete \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "name": "mem_71ab" }'
```

Address a memory by `id` or by `name`; `id` wins when both are present.

## Memory or Knowledge?

Two different stores, and picking the wrong one is the common mistake:

- **Memory** — per user, small, written as you go. What this assistant should
  remember about this person.
- **[Knowledge](/docs/knowledge)** — per org, a wiki plus ingested sources plus
  agent memory in one graph. What the organization knows.

They are separate systems and neither reads the other.
