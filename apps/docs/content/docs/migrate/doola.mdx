Doola forms a US company: you pick a structure, give it people and addresses, pay
the fee, sign, and the state files it. `/v1/company` (22 operations) is a guarded
state machine over the same steps, with the edges as the only doors between them.

## Nouns

| Doola | Hanzo |
|---|---|
| `POST /v1/partner/companies` | `POST /v1/company` — begins the org's one formation |
| `entityType` — `LLC` or `CCorp` | `structure` — `c-corp`, `llc` or `dao-llc` |
| `state` — `WY`, `DE` | `jurisdiction` — `DE` or `WY` |
| `nameOptions` | `name` on `PUT /v1/company/structure` |
| `members` / `executiveMembers` | `founders` — `POST /v1/company/founders`, each with `equityBps` |
| Company status you follow by webhook | `stage` on the formation, with `nextStages` beside it |
| Advancing the formation | `POST /v1/company/advance` — the only door between stages |
| `POST /v1/partner/companies/{id}/signatures` | `POST /v1/company/esign`, settled by `POST /v1/company/esign/complete` |
| Formation documents | `POST /v1/company/documents`, ingested into the org's data room |
| KYC on the responsible party | `POST /v1/company/kyc` · `/kyc/refresh` · `/kyc/decision` |
| Paying the formation fee | `POST /v1/company/payment` |
| Onboarding a company that already exists | `POST /v1/company/skip`, then `/import/captable` and `/import/documents` |
| Reading the formation | `GET /v1/company` |

Two paths reach the end. **Incorporate** is `structure → founders → payment →
documents → esign → genesis → company`, each edge guarded by the step before it.
**Import** is `structure → import → company`, for an entity that already exists
and brings its own cap table and documents.

## The call

Doola — a customer, then a company for them:

```bash
curl -X POST https://api.test.doola.com/v1/partner/customers \
  -H "Authorization: dk_test_your_api_key_here" \
  -H "Idempotency-Key: customer-001" \
  -H 'Content-Type: application/json' \
  -d '{
    "email": "ada@example.com",
    "firstName": "Ada",
    "lastName": "Lovelace",
    "phoneNumber": "+12125550100",
    "countryOfResidence": "USA"
  }'

curl -X POST https://api.test.doola.com/v1/partner/companies \
  -H "Authorization: dk_test_your_api_key_here" \
  -H "Idempotency-Key: company-001" \
  -H 'Content-Type: application/json' \
  -d '{
    "doolaCustomerId": "3GS9gyeBDENq7kvAv818oPITfyh",
    "entityType": "CCorp",
    "state": "DE",
    "nameOptions": [{"name": "Acme Robotics", "entityTypeEnding": "Inc."}],
    "industry": "Custom Computer Programming Services",
    "description": "Robotics hardware and software."
  }'
```

Hanzo:

```bash
# 1. Begin. Idempotent — an org that already has a formation gets that one back
#    with 200, while a first call creates it and answers 201.
curl -X POST https://api.hanzo.ai/v1/company \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"structure": "c-corp", "jurisdiction": "DE", "name": "Acme Robotics"}'

# 2. The people, and what each holds in basis points.
curl -X POST https://api.hanzo.ai/v1/company/founders \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "founders": [
      {"name": "Ada Lovelace", "email": "ada@example.com", "equityBps": 10000}
    ]
  }'

# 3. Move. An edge the machine does not define answers 409; an edge whose guard
#    is unsatisfied answers 422 naming exactly what is missing.
curl -X POST https://api.hanzo.ai/v1/company/advance \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"to": "payment"}'
```

Every write answers the whole formation plus `nextStages`, so the next legal
move is in the reply to the last one. That is the loop: act, read `nextStages`,
advance.

## What does not carry

**This is not a partner API.** Doola forms companies for *your* customers, many
per tenant, keyed by `doolaCustomerId`. `/v1/company` forms *this org's own*
company, and there is exactly one. If you were reselling formation, that model
does not port. `GET /v1/company/register` is the platform's own book across every
org — a queue to work, not a place to file for a customer.

**No formation webhooks.** Doola tells you not to poll and pushes progress.
Progress here is `stage`, read with `GET /v1/company` or returned by whatever
call you just made.

**No reference data.** There are no endpoints for states, NAICS codes, state
filing fees or countries. `structure` and `jurisdiction` are closed sets — an
unknown value, or an empty name, is a 400 at `PUT /v1/company/structure`.

**No industry classification.** `industry`, `description` and NAICS have no
field on the formation.

**No sandbox playground.** Doola gives you two sandbox-only endpoints that
complete formation and EIN issuance on demand so you can exercise the whole
integration. Nothing here fast-forwards the machine.

**Non-US founder mechanics are not modelled.** SS-4 and Form 8821 signature
flows, and expedited EIN, are doola features with no field on this side.

**Filing is honest about being unwired.** With no filing partner configured the
filing is recorded as `manual` and no filing id is fabricated. Check
`filing.status` rather than assuming a document render means a submission.

**There is a step doola does not have.** Reaching the terminal `company` stage
records the incorporation on the org's canonical cap table, and that write must
succeed before the transition is persisted — so a formation that says `company`
always has a cap table behind it.
