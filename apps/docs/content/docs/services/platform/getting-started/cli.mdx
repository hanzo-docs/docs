The `hanzo` CLI reaches every product of the cloud from the terminal — clusters,
projects and deploys, logs, secrets and keys. It talks to the same API, on the
same contract, as the dashboard and the SDKs.

## Installation

```bash
curl -fsSL hanzo.sh | sh
```

That downloads one prebuilt native binary per tool — `hanzo`, `hanzo-mcp` and
`dev` — verifies each against its published sha256, and puts them in
`~/.local/bin`. Nothing is compiled, and no package manager or runtime is
involved. Set `HANZO_INSTALL_DIR` to install somewhere else.

To take a single tool instead of all three:

```bash
curl -fsSL hanzo.sh/cli | sh   # the hanzo CLI alone
curl -fsSL hanzo.sh/mcp | sh   # the MCP server alone
```

On macOS you can install the CLI from the tap instead:

```bash
brew install hanzoai/tap/hanzo
```

Binaries for every platform are also published on
[GitHub Releases](https://github.com/hanzoai/cli/releases).

Verify the installation:

```bash
hanzo version
```

## Authentication

Sign in through [Hanzo IAM](https://hanzo.id) over OIDC:

```bash
hanzo auth login
```

That opens a browser to finish the round trip, then writes the credential to a
file of its own with mode `0600` — never into the config. Every later command
reads it from there.

<Callout type="warn">
  It is `hanzo auth login`, not `hanzo login`. A first word the CLI does not
  recognize is read as a task to work on, so `hanzo login` starts a coding
  session about the word "login" instead of signing you in.
</Callout>

The CLI holds several identities at once and marks one active:

```bash
# Who am I, and in which org
hanzo auth show

# Every identity held, active one marked
hanzo auth list

# Switch the active identity (bare form toggles when you hold exactly two)
hanzo auth use

# Sign out one identity, or --all
hanzo auth logout
```

For CI, sign in non-interactively and keep the credential off the command line —
`--token -` reads it from stdin, never from argv:

```bash
printf '%s' "$CI_SECRET" | hanzo auth login --provider hanzo --token -
```

To hand the bearer to another tool, print it rather than copying it out of a
file:

```bash
curl -H "Authorization: Bearer $(hanzo auth token)" https://api.hanzo.ai/v1/models
```

## Core Commands

Each command group is one cloud product, and its subcommands are that product's
operations — generated from the same contract the API, the SDKs and the MCP
tools serve. `hanzo --help` lists every group; `hanzo <group> --help` lists its
verbs.

### Clusters

```bash
# Every cluster in the org: managed node pools and attached BYO clusters
hanzo clusters list

# Attach a cluster you already run — the kubeconfig is validated and KMS-sealed
hanzo clusters create --name prod-k8s --kubeconfig ./kubeconfig.yaml

# Node pools
hanzo clusters pools scale <cluster-id> <pool-id> --count 3

# Detach a cluster (does not delete the infrastructure)
hanzo clusters rm <cluster-id>
```

### Projects

A project is the handle a site is deployed and served under.

```bash
# Every project the org owns
hanzo projects list

# One project: settings, live URL, and the deployment serving it
hanzo projects get <slug>

# Create one
hanzo projects create --name my-app --framework next

# Deploy a build to it
hanzo projects deploy <slug>

# Deployment history, newest first
hanzo projects deployments list <slug>

# Flush the edge cache without redeploying
hanzo projects purge <slug>

# Take the site off the internet
hanzo projects rm <slug>
```

### Domains

```bash
hanzo projects domains list <slug>
hanzo projects domains create <slug> --domains app.example.com
hanzo projects domains verify <slug> <host>
```

### Logs

```bash
# Search the org's logs by label, time and substring
hanzo logs query

# Append structured records
hanzo logs write

# How many records this deployment holds
hanzo logs health
```

### Secrets and keys

Secrets live in [KMS](/docs/services/kms); API keys are minted from IAM. Neither
is stored on disk by the CLI.

```bash
# Secrets
hanzo kms secrets list
hanzo kms secrets get <path>
hanzo kms secrets create
hanzo kms secrets rm <path>

# API keys — create returns the key ONCE
hanzo keys get
hanzo keys create --type <type>
hanzo keys clear --type <type>
```

### Organizations

```bash
# Create an org
hanzo orgs create --name acme-corp

# What the org is entitled to
hanzo orgs entitlements get

# Org settings
hanzo org settings get
```

### Continuous delivery

`hanzo deploy` is the CD control plane — what each application reconciles from
and how the last sync ended:

```bash
hanzo deploy gitops
hanzo deploy applications
hanzo deploy health
```

## Global Flags

Valid on every subcommand:

| Flag | Description |
|------|-------------|
| `-c`, `--config <FILE>` | Use a different config file for this invocation |
| `-v`, `--verbose` | Increase logging verbosity (repeat for more) |
| `-V`, `--version` | Print the CLI version |
| `--help` | This page, or a subcommand's own help |

## Configuration

Settings are TOML, in one file:

| | |
|---|---|
| Linux | `~/.config/hanzo/config.toml` |
| macOS | `~/Library/Application Support/hanzo/config.toml` |

```toml title="config.toml"
[auth]
provider = "hanzo"

[auth.active]
hanzo = "acme-corp/alice"

[code]
theme = "auto"
```

Read and write it through the CLI rather than by hand — keys are dotted:

```bash
hanzo config list
hanzo config get network.active
hanzo config set code.theme auto
```

`--config <FILE>` points a single invocation at a different file.

<Callout type="info">
  The config file holds **no secrets**. Credentials are written separately, mode
  `0600`, to `~/.local/share/hanzo/credentials` on Linux and
  `~/Library/Application Support/hanzo/credentials` on macOS — managed entirely
  by `hanzo auth`, never edited by hand.
</Callout>

The API host every command calls is `https://api.hanzo.ai`, and every path is
under `/v1/`. It is already the default, so a normal install has nothing to set.

Precedence is flag → config file → built-in default.
