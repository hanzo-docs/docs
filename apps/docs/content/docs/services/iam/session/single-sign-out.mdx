## Overview

Hanzo IAM implements **OIDC RP-initiated logout**. One endpoint ends the browser
session and retires the tokens the calling application holds:

```http
GET or POST /v1/iam/oauth/logout
```

It is the `end_session_endpoint` in the discovery document, so a client never
needs to hard-code it:

```bash
curl -s https://iam.hanzo.ai/.well-known/openid-configuration \
  | jq -r .end_session_endpoint
# https://hanzo.id/v1/iam/oauth/logout
```

<Callout type="warn">
There is no org-wide "log out of everything" endpoint, and no `logoutAll`
parameter. Sign-out is scoped to **(user, application)** on purpose: signing out
of one app must not silently tear down every other app the same person is signed
into. If you need a fan-out sign-out, see [Ending every
session](#ending-every-session) below.
</Callout>

<Callout type="warn">
IAM serves a `200 text/html` SPA for any **unregistered** path. A wrong path
therefore returns 200 HTML, not 404 — so a probe that "works" proves nothing.
Use the exact paths on this page, or read them from discovery.
</Callout>

## What logout does

Three things happen, in this order:

1. **The browser session dies.** The `sid` is revoked server-side *and* the
   cookie is expired. Server-side revocation is the load-bearing half — a copy
   of the cookie taken before logout must not still resolve.
2. **The relying party's grant is retired.** When a verified `id_token_hint`
   names an application, every token row that (user, application) holds is
   deleted, along with the whole refresh-rotation family each belongs to. The
   family sweep is what makes it a revocation rather than a gesture: a refresh
   chain rotates into *new* rows, so deleting only the rows found by (user, app)
   can leave a rotated descendant alive and mintable. With no hint, the
   application named by the session itself is used, so a plain browser logout
   still leaves no mintable refresh token behind.
3. **Only then is a redirect considered**, and only to a **registered** URI.

## Parameters

| Parameter | Required | Meaning |
|---|---|---|
| `id_token_hint` | no | The ID token from the session being ended. It is **verified**; a forged or unsigned one is ignored. This is the only thing that can name an application, for both the revocation and the redirect. |
| `post_logout_redirect_uri` | no | Where to send the browser afterwards. Honored **only** when a verified `id_token_hint` identifies the application and that application has registered this exact URI. Anything else falls through to the ordinary response — nobody can turn your logout link into a redirect of their choosing. |
| `state` | no | Opaque value appended to `post_logout_redirect_uri` on redirect. |

## Response

An API caller gets JSON:

```json
{ "status": "ok" }
```

A browser *navigating* to the endpoint gets a `302` to the issuer's own
`/login?signed_out=1` page, so a white-labelled brand lands on its own page.

The choice is made from `Accept` alone, with one carve-out: an explicit
`X-Requested-With: XMLHttpRequest` or a JSON preference always wins. The default
is JSON, so nothing that parses this endpoint today starts receiving a redirect.

## Examples

### Plain sign-out

```bash
curl -X POST https://api.hanzo.ai/v1/iam/oauth/logout \
  --cookie "__Host-hanzo_session=abc123def456"
```

### Sign-out naming the relying party

Pass the ID token so IAM can revoke that application's grant and honor a
registered return URI:

```bash
curl -X POST https://api.hanzo.ai/v1/iam/oauth/logout \
  -d "id_token_hint=$ID_TOKEN" \
  -d "post_logout_redirect_uri=https://app.example.com/signed-out" \
  -d "state=xyz"
```

### As a link

The endpoint accepts `GET`, so it works as a plain anchor:

```html
<a href="https://api.hanzo.ai/v1/iam/oauth/logout?id_token_hint=…&post_logout_redirect_uri=https%3A%2F%2Fapp.example.com%2Fsigned-out">
  Sign out
</a>
```

### From the browser

```javascript
await fetch('https://api.hanzo.ai/v1/iam/oauth/logout', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
  body: new URLSearchParams({ id_token_hint: idToken }),
  credentials: 'include',   // required — the session cookie is what gets cleared
});

// Then clear whatever your app kept locally.
localStorage.removeItem('access_token');
sessionStorage.clear();
window.location.href = '/login';
```

## Using the SDK

Never hand-roll the flow. `@hanzo/iam` owns the paths (it hard-codes these same
values as the fallback when discovery fails) and clears local token state for
you:

```typescript
import { configureIam, logout } from '@hanzo/iam';

configureIam({
  issuer: 'https://iam.hanzo.ai',   // or serverUrlForBrand('lux') → https://lux.id
  clientId: 'hanzo-myapp',          // client_id is always <org>-<app>
});

await logout();   // RP-initiated logout + local token clear
```

## Revoking a token directly

Logout is a *session* operation. To retire a single credential — someone signed
out on another device, or a token may have leaked — use RFC 7009 revocation:

```http
POST /v1/iam/oauth/revoke
```

```bash
curl -X POST https://api.hanzo.ai/v1/iam/oauth/revoke \
  -d "token=$REFRESH_TOKEN" \
  -d "client_id=hanzo-myapp"
```

Revoking an **access** token kills that token. Revoking a **refresh** token
kills the whole rotation family it belongs to, so no further access tokens can
be minted from it and every token already minted from it dies with it.

Public clients may revoke, and must: sign-out is the only control a long-lived
refresh token has. A token that is not yours, or that never existed, answers
success and does nothing — so the endpoint cannot be used to discover which
tokens are real.

## Ending every session

IAM has no fan-out sign-out. To end a person's sessions everywhere, the calling
application does it explicitly:

1. List their live sessions with `POST /v1/iam/sessions/list` (the session
   surface is typed ops, so every call is a `POST` — `list`, `get`, `create`,
   `update`, `delete`).
2. `POST /v1/iam/sessions/delete` each one, and `POST /v1/iam/oauth/revoke` each
   refresh token they hold. One revoke call retires that token's whole rotation
   family.

Because revocation deletes the rows, a refresh attempt afterwards fails with
`invalid_grant` rather than minting a fresh access token.

<Callout type="warn">
An **already-issued access token stays syntactically valid until it expires.**
A JWT's `exp` reads valid for as long as it was minted for, so revocation
state — not expiry — is what is authoritative. If your service must reject a
revoked token before its `exp`, call `POST /v1/iam/oauth/introspect` rather than
verifying the signature alone.
</Callout>

## Troubleshooting

**A token still works after logout.** Logout retires the grant for *one*
application. Another application's tokens are untouched by design — revoke them
explicitly. And an access token already in flight remains verifiable until
`exp`: introspect if you need immediate rejection.

**Logout returned HTML instead of JSON.** Your client sent
`Accept: text/html`. Send `Accept: application/json` or
`X-Requested-With: XMLHttpRequest`.

**Logout returned `200` but nothing happened.** You probably hit an
unregistered path and got the SPA catch-all. Confirm against
`.well-known/openid-configuration`.

**The redirect was ignored.** A `post_logout_redirect_uri` is honored only with
a verified `id_token_hint` *and* only when that application has registered the
exact URI. Register it on the application, then retry.

**The session cookie was not cleared.** A browser call needs
`credentials: 'include'`, and the request must reach IAM's origin — a proxy that
strips cookies leaves the session alive.
