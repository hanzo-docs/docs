**Enterprise buyers demand strict tenant isolation, their own SSO, and zero cross-customer model leakage.** Hanzo's multi-tenancy model gives every customer organization its own IAM boundary, Base namespace, KMS prefix, billing ledger, and entitlement set out of the box.

## Tenant isolation boundary

| Layer | Isolation mechanism | Endpoint |
|---|---|---|
| **Identity & SSO** | Dedicated organization under Hanzo IAM (`hanzo.id`) with OIDC/SAML | `/v1/iam/organizations` |
| **Application data** | Org-isolated Hanzo Base instance & GraphQL endpoint | `/v1/base/bases/{org}` |
| **Secrets** | Per-org KMS encryption namespace | `/v1/kms/secrets` |
| **Entitlements & quotas** | Plan subscriptions and resolved runtime entitlements | `/v1/plan`, `/v1/entitlement/orgs/{org}` |
| **Intelligence** | Org-private Kai capabilities, Enso feedback ledgers, and Zen LoRA artifacts | `/v1/capabilities`, `/v1/train/artifacts` |

## Provision & inspect tenant entitlements

<Tab value="CLI">
```bash

hanzo iam organizations list
hanzo plan list

# Inspect resolved entitlements for a tenant org
hanzo entitlement orgs get acme-corp
```

import { Configuration, IamApi, EntitlementApi, PlanApi } from 'hanzoai';

const cfg = new Configuration({ accessToken: process.env.HANZO_API_KEY });

  new PlanApi(cfg).getPlan(),

## White-label checklist

1. Never reuse a single shared `sk-` server key without passing verified tenant isolation boundaries.
2. Separate `pk-` publishable browser keys from `sk-` server credentials ([API keys](/docs/api-keys)).
3. Attach custom domains and TLS via `/v1/domain` and `/v1/ingress`.
