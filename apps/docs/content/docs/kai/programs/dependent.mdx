**A dependent question reads another question's answer.** "Which billing
issue is it?" only makes sense once the team is billing. The parent's answer
decides which child to ask, and the child can read that answer.

Over `/v1/decisions` the questions of one request are answered independently
of each other; a request cannot say that one depends on another. Chain calls
instead, as below. Program requests will arrive on the same endpoint.

## In Kai's runtime

In process, a program's questions name their parents, and a scheduler asks
them in passes:

| Pass | What it asks |
|---|---|
| 1 | every question, nothing known; an answer whose top probability reaches a threshold is frozen and never asked again |
| a wave per depth | every question whose parents have settled, in one pass, with the parents' answers added to the state as facts |
| pairwise | for a parent still unsure, each of its likeliest answers set in turn, to see how each moves its children |
| last | the most probable joint answer over the candidates, projected onto the program's rules ([Repair](/docs/kai/programs/repair)) |

Questions on independent branches go in the same wave, so the number of
passes follows the depth of the graph, at most depth + 2, not the number of
questions. The joint slot decoder, which reads known answers directly in one
decode, has been trained only as a pilot and is not served.

## Chain it today

Ask the parent. If its answer clears your threshold, ask the child question
that goes with it, and put the parent's answer at the front of the state
under `facts`, in the shape the scheduler uses: type, question, and the
chosen option's text.

```python
def fact(question: Choice, label: str) -> dict:
    """A parent's answer as the native scheduler states it to a child: type, question, and the chosen option's text."""
    return {"type": "choice", "question": question.instructions, "answer": f"{label}: {question.criteria[label]}"}


with Kai(retry=RetryPolicy(max_retries=10)) as kai:
    for ticket in TICKETS:
        state = {"ticket": ticket}
        team = kai.decide(state=state, questions={"team": TEAM}).choices["team"]
        print(f"{ticket}\n  team   {team.choice} p={team.answer_confidence}")
        if team.answer_confidence < THRESHOLD:
            print("  stop: the team is under its threshold; a person routes this one")
            continue
        child = {"issue": ISSUE[team.choice]}
        told = kai.decide(state={"facts": {"team": fact(TEAM, team.choice)}, **state}, questions=child).choices["issue"]
        blind = kai.decide(state=state, questions=child).choices["issue"]
        print(f"  issue  {told.choice} p={told.answer_confidence} with the fact; {blind.choice} p={blind.answer_confidence} without")
```

## What the run shows

- **The chain asks only the question that applies.** Four tickets reach the
  right team and a child question written for it.
- **A wrong parent sends the child to the wrong question.** The Okta sign-in
  ticket goes to billing, above the 0.5 threshold, so the chain asks it a
  billing question and gets `plan_change`. The threshold did not catch it; set
  it from cases whose answer you know, not by guess.
- **The fact did not help here.** Each child chose the same label with and
  without it, except the CSV ticket, whose two answers were both wrong (it
  times out, so `slow`), and the fact lowered the child's probability every
  time. Keep the fact only if it helps on your own cases; the structure, one
  child per parent answer, is what the chain buys.
