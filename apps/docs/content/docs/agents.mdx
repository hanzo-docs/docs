# Agents

An agent is a stored configuration: a model, a system prompt, and a set of tools.
You define it once in your org, then run it by name. Every run is recorded — its
input, its output or its error, the model that answered, and how long it took.

## Define one

```bash
curl -X POST https://api.hanzo.ai/v1/agents \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "researcher",
    "model": "enso-flash",
    "instructions": "Summarize customer feedback. Be terse and cite the source.",
    "tools": ["search", "fetch"]
  }'
```

`name` must be unique in your org and match
`^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`. Omit `model` and the deployment's default is
used; name one and it is checked against the catalogue the gateway actually
serves, so a model this deployment never serves is refused here rather than
failing later at run time.

`description`, `executionMode`, `computeRef`, and `serviceAccountId` are
optional. An agent meant to run on a timer must carry `schedule` as a five-field
cron expression — the scheduler would otherwise never fire it — and scheduled
agents count against a per-org cap.

## Run it

```bash
curl -X POST https://api.hanzo.ai/v1/agents/researcher/run \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "input": "Summarize Q3 customer feedback." }'
```

The path segment is a **ref** — either the agent's `agent_…` id or its
org-unique name. Both resolve the same agent, and an agent in another org is a
`404`, exactly like one that does not exist.

You get back the run that was recorded:

```json
{
  "id": "run_5c1e",
  "status": "ok",
  "model": "enso-flash",
  "input": "Summarize Q3 customer feedback.",
  "output": "Three themes dominate...",
  "durationMs": 2140,
  "createdAt": "...",
  "traceId": "tr_9ab2",
  "promptTokens": 1204,
  "completionTokens": 188
}
```

**A failed run is a `502` whose body is the run, not an error envelope.** The
execution happened, it is in the agent's history, and its `error` field is the
product — a client that treats every non-2xx as opaque throws away the only
account of what went wrong.

A transient upstream failure is retried with backoff, and a configured failover
model is tried before a run is called an error. Your balance is authorized
before any inference, so an unfunded org gets `402` rather than free compute.
Only successful runs are billed, attributed to the model that actually answered —
a run that failed over bills the model it fell over to.

## Read the history

```bash
# One agent's runs, newest first
curl https://api.hanzo.ai/v1/agents/researcher/runs \
  -H "Authorization: Bearer $HANZO_API_KEY"

# Every agent's runs across the org — what broke, specifically
curl "https://api.hanzo.ai/v1/agents/runs?status=error&limit=20" \
  -H "Authorization: Bearer $HANZO_API_KEY"
```

The org-wide feed answers "what is my agent plane doing" without needing to know
an agent name first. `limit` is 1–200 and reads as 50 when absent; `status` keeps
only `ok` or only `error`.

## Manage them

`GET /v1/agents` lists them, `GET /v1/agents/{ref}` reads one with its recent
runs and instructions, `PATCH /v1/agents/{ref}` edits, `DELETE /v1/agents/{ref}`
removes.

## Watching a run live

Every run opens a session on the live agent plane, so a long run is visible — and
interruptible — while it happens. See [Mission Control](/docs/mission-control) for
pausing, resuming, stopping, and messaging a running agent.

Runs also carry a `traceId`, which takes you from the recorded run to the full
waterfall of that same execution in [Traces](/docs/traces).
