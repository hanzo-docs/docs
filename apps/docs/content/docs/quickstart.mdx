**After this page you have a working credential and one call that answered.**

Hanzo is one cloud behind one key. Every capability — inference, identity,
storage, money, agents — answers at `https://api.hanzo.ai`, and the CLI, the
SDKs and the MCP tools are all generated from the same description of it. So
there is nothing to wire up per service: get a key once and everything is
reachable.

## 1. Install

<Tabs items={['npm', 'Script', 'Homebrew', 'From source']}>
<Tab value="npm">
```bash
npm i -g hanzo
```

`hanzo` is the CLI and the client in one install.
</Tab>
<Tab value="Script">
```bash
curl -fsSL https://hanzo.sh | sh
```

Installs into `~/.local/bin`. `https://hanzo.sh/cli` installs the CLI alone.
</Tab>
<Tab value="Homebrew">
```bash
brew install hanzoai/tap/hanzo
```
</Tab>
<Tab value="From source">
```bash
git clone https://github.com/hanzoai/cli && cd cli && cargo install --path .
```
</Tab>
</Tabs>

```bash
hanzo version
```

## 2. Log in

```bash
hanzo auth login
```

That opens a browser against [hanzo.id](https://hanzo.id), Hanzo's identity
provider, and stores the resulting credential locally. `hanzo auth show` prints
who you are; `hanzo auth list` shows every identity on this machine and
`hanzo auth use` switches between them.

For a server, mint a key instead of logging a person in: **console.hanzo.ai →
API keys**. A secret key resolves to *you*, so it belongs on a server and never
in a browser — [Authentication](/docs/api-keys) is the whole rule.

```bash
export HANZO_API_KEY=sk-...
```

## 3. List the models

The catalogue of models the gateway currently serves. It is a read, it needs
nothing but the key, and it is the same operation on all four surfaces.

<Tabs items={['CLI', 'SDK', 'HTTP', 'MCP']}>
<Tab value="CLI">
```bash
hanzo models list
```
</Tab>
<Tab value="SDK">
<Tabs items={['.ts', '.py', '.go', '.rs']}>
<Tab value=".ts">
```bash
npm i hanzoai
```

```typescript
import { AiApi, Configuration } from 'hanzoai'

const ai = new AiApi(new Configuration({ accessToken: process.env.HANZO_API_KEY }))
const { data } = await ai.getModels()
```
</Tab>
<Tab value=".py">
```bash
pip install hanzoai
```

```python
import os
from hanzoai.cloud import ApiClient, Configuration
from hanzoai.cloud.api import AiApi

client = ApiClient(Configuration(access_token=os.environ["HANZO_API_KEY"]))
models = AiApi(client).get_models()
```
</Tab>
<Tab value=".go">
```bash
go get github.com/hanzoai/go-sdk
```

```go
cfg := hanzoai.NewConfiguration()
cfg.AddDefaultHeader("Authorization", "Bearer "+os.Getenv("HANZO_API_KEY"))
client := hanzoai.NewAPIClient(cfg)

models, _, err := client.ModelsAPI.AiListModels(context.Background()).Execute()
```
</Tab>
<Tab value=".rs">
```bash
cargo add hanzo-client
```

```rust
use hanzo_client::apis::{ai_api, configuration::Configuration};

let mut cfg = Configuration::new();
cfg.bearer_access_token = std::env::var("HANZO_API_KEY").ok();

let models = ai_api::get_models(&cfg).await?;
```
</Tab>
</Tabs>

Each client is generated from the same description of the API, so the class and
the method both follow from the operation rather than from a hand-written
wrapper — and each carries every `/v1` capability, not just this one. The client
is regenerated per language on its own release schedule, so a method name here
can be a release behind the one the [reference](/docs/openapi) prints; the
reference says so on the operation when it is. [Java, Kotlin, Swift and
C++](/docs/sdks) are at earlier stages — that page says exactly which are on a
registry today.
</Tab>
<Tab value="HTTP">
```bash
curl https://api.hanzo.ai/v1/models \
  -H "Authorization: Bearer $HANZO_API_KEY"
```
</Tab>
<Tab value="MCP">
```bash
curl -X POST https://api.hanzo.ai/v1/mcp \
  -H "Authorization: Bearer $HANZO_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

One endpoint, one tool per capability. `tools/call` names the capability and the
operation; `describe` explains any operation's input.
</Tab>
</Tabs>

Those are one API seen from four places, and the tabs above are the whole
difference. Pick the one you will write in:

- **[CLI](/docs/cli)** — every capability as a command group, one page each.
- **[SDKs](/docs/sdks)** — TypeScript, Python, Go and Rust on a registry today;
  Java, Kotlin, Swift and C++ behind them. Generated from the same description
  the CLI and the tools are.
- **[MCP](/docs/mcp)** — one endpoint an agent connects to; [the tools](/docs/mcp-tools)
  are listed one per capability.

HTTP needs no page: it is `https://api.hanzo.ai` and the key you just exported.

## 4. Send a completion

This is the first step that draws down credit; everything above is free to run.

```bash
hanzo chat completions --model zen-1 --messages '[{"role":"user","content":"hello"}]'
```

Then read what it drew down:

```bash
hanzo billing balance
hanzo usage summary
```

[Credits & billing](/docs/credits) explains what a credit is and what happens at
zero; [Pricing](/docs/pricing) is the rate for every model and tool.

## 5. Run the cloud locally

The same binary that serves `api.hanzo.ai` runs on your machine:

```bash
hanzo up cloud
```

Bare `hanzo up` is the same thing — `cloud` is the default. Name one service to
run it alone: `hanzo up iam`, `hanzo up kms`, `hanzo up gateway`, `hanzo up
storage`, `hanzo up pubsub`. See [Run your own](/docs/network) for what that
means and what it needs.

## When something does not answer

The CLI describes itself, so the fastest answer is usually local:

```bash
hanzo --help              # every capability as a command group
hanzo billing --help      # and every command inside one
```

Support is a capability like any other, which means you can reach it from the
same key you just exported — `hanzo help articles list` reads the knowledge
base, `hanzo help tickets` opens a ticket, and both are `/v1/help` if you would
rather call them over HTTP. [Errors](/docs/errors) explains what a status code
from `api.hanzo.ai` means before you open one.
