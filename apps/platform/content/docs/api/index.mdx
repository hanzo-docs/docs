Everything the dashboard does, it does over one public HTTP surface. There is no
second protocol and no second host.

## Base URL

```
https://api.hanzo.ai/v1
```

<Callout type="warn">
`app.platform.hanzo.ai` is the **dashboard**, not an API host. It answers `301`
on every path and redirects to `platform.hanzo.ai`, and `curl` silently
downgrades a `POST` to a `GET` when it follows a `301`. Point programmatic calls
at `api.hanzo.ai`.
</Callout>

## Surfaces

Three groups of resources live under `/v1`. They are separate services behind one
host, which is why the path prefixes differ.

| Prefix | Resource | Docs |
|--------|----------|------|
| `/v1/platform/projects/…` | Projects, apps, deploys, env, domains | [Containers](/docs/api/containers) |
| `/v1/machines`, `/v1/gpus`, `/v1/clusters`, `/v1/k8s/…` | Machines, GPUs, clusters, node pools | [Clusters](/docs/api/clusters) · [Machines](/docs/api/vms) |
| `/v1/iam/…` | Organizations, roles, invitations | [Organizations](/docs/api/organizations) |

## Authentication

Every request carries a bearer token, and every request acts as exactly one
organization:

```bash
curl https://api.hanzo.ai/v1/platform/projects \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "X-Org-Id: acme-corp"
```

A call with no validated principal, or one whose token is not bound to a single
org and carries no `X-Org-Id`, is refused `403` with
`{"status":403,"code":"forbidden","error":"X-Org-Id required"}`. See
[Authentication](/docs/api/authentication) for how to obtain a token.

## Request Format

The HTTP method carries the verb; the path names the resource. Writes take a JSON
body:

```bash
curl -X POST https://api.hanzo.ai/v1/platform/projects/my-app/apps \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "X-Org-Id: acme-corp" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "web",
    "source": "image",
    "image": { "repository": "ghcr.io/myorg/web", "tag": "v1.2.3" },
    "port": 3000
  }'
```

## Response Format

Success returns the resource itself — no envelope:

```json
{
  "id": "app_abc123",
  "slug": "web",
  "name": "web",
  "environment": "production",
  "source": "image",
  "image": { "repository": "ghcr.io/myorg/web", "tag": "v1.2.3" },
  "port": 3000,
  "replicas": 1,
  "status": "running"
}
```

## Error Responses

Errors return the matching HTTP status with a three-field body:

```json
{
  "status": 403,
  "code": "forbidden",
  "error": "X-Org-Id required"
}
```

| Status | Meaning |
|--------|---------|
| `400` | Invalid input |
| `401` | Missing or invalid token |
| `403` | No validated principal, or no organization |
| `404` | Resource does not exist |
| `409` | Slug or host already claimed |
| `429` | Too many in-flight builds or deploys — retry |
| `500` | Server error |

Every response carries `x-request-id`; quote it when reporting a problem.

## Concurrency Limits

Deploys, not reads, are what the platform bounds. Concurrent in-flight image
deploys are capped per organization and concurrent builds are capped in the
cluster; over the cap a deploy is refused `429` and is safe to retry. Reads are
not rate-limited by the platform.
